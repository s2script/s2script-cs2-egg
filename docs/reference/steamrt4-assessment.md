# SteamRT4 migration assessment

Research checked 2026-11-10 against pre-migration commit `9517796`. This note records the assessment before implementation; the user subsequently selected an RT4-only v2.0.0. See the [implementation design](../superpowers/specs/2026-11-10-steamrt4-v2-design.md) and [upgrade instructions](../upgrading.md#v200-steamrt4) for the selected behavior.

## What changes upstream

| Component | SteamRT3 (`sniper`) | SteamRT4 (`steamrt4`) |
| --- | --- | --- |
| Distribution foundation | Debian 11 Bullseye | Debian 13 Trixie |
| glibc in the inspected platform manifest | 2.31 | 2.41 |
| `libstdc++6` implementation | GCC 10.3 | GCC 14.2 |
| Other dependency examples | `libssl1.1`, `libffi7`, `libcurl4` | `libssl3t64`, `libffi8`, `libcurl4t64` |
| x86 architectures | amd64 and i386 | amd64 and i386 |

Sources: Valve's [runtime goals](https://github.com/ValveSoftware/steam-runtime/blob/master/doc/goals.md), [RT3 platform manifest](https://repo.steampowered.com/steamrt3/images/latest-container-runtime-depot/com.valvesoftware.SteamRuntime.Platform-amd64,i386-sniper.manifest.dpkg), and [RT4 platform manifest](https://repo.steampowered.com/steamrt4/images/latest-public-stable/com.valvesoftware.SteamRuntime.Platform-amd64,i386-steamrt4.manifest.dpkg). These are runtime-library versions, not a claim that CS2 itself will be rebuilt with a different compiler.

RT4 is a released runtime with a public-stable channel, not merely an unreleased experiment. The [RT4 public-stable directory](https://repo.steampowered.com/steamrt4/images/latest-public-stable/) resolved to `4.0.20261021.265997`; [RT3's depot directory](https://repo.steampowered.com/steamrt3/images/latest-container-runtime-depot/) resolved to `3.0.20261021.266025`. Both received October 2026 builds. This is evidence that RT3 is still being published, not a guarantee of a future support period.

Valve now recommends RT4 for new native Linux games and allows existing developers to select it when updating their games. Valve still documents RT3 separately. See the [official Steam Runtime README](https://github.com/ValveSoftware/steam-runtime). This general recommendation is **not a CS2 dedicated-server RT4 requirement**. No current Valve statement specifically mandating RT4 for CS2 dedicated servers was verified in this research. No runtime smoke test was performed, so successful CS2/addon operation under RT4 is also not established here.

## Real benefits and limits

The concrete benefit is a newer userspace baseline: access to newer glibc/C++ symbols and newer library families for future game or addon binaries. That can remove incompatibilities when an upstream addon raises its minimum requirements. It also puts the image on Valve's currently recommended generation. Those are compatibility and maintenance benefits inferred from the manifests and Valve's recommendation above.

No primary-source controlled benchmark was found establishing better CS2 server frame times, tick stability, player capacity, latency, or lower CPU/RAM use from this change. A newer library version alone does not establish those outcomes. The same precompiled CS2 executable would still run, and the container continues using its host kernel. Measure any claimed improvement on the same host, game build, map, addon versions, and load before attributing it to RT4. Graphics/Proton improvements are not useful evidence for a headless native dedicated server.

## Compatibility work that matters

- **Audit package names and ELF dependencies.** The manifest changes include actual library-generation changes, not just package updates. Check `DT_NEEDED`, unresolved symbols, and the libraries selected through `LD_LIBRARY_PATH` for the game and every plugin. Inference: older glibc-targeted binaries often work on a newer glibc, but this does not cover a missing library SONAME, private ABI assumptions, or plugin/game interfaces.
- **Preserve SteamCMD's i386 environment.** RT4's x86 platform manifest includes i386 glibc and C++ runtime packages, so RT4 is not inherently a 64-bit-only replacement. Validate the existing SteamCMD bootstrap/login/app-update path as part of the image test; package presence alone does not verify that path. This research did not independently inspect the SteamCMD executable.
- **Inspect executable-stack flags.** glibc 2.41 changed dynamic loading: a module requiring an executable stack can fail to load when the process stack is not executable. Missing `PT_GNU_STACK` can also matter. Inspect `readelf -lW` on addon libraries, prefer maintained rebuilt binaries, and test actual plugin loads. Clearing a flag without establishing that the plugin does not need an executable stack is not a compatibility proof. See the [glibc implementation change](https://sourceware.org/pipermail/glibc-cvs/2024q4/086970.html) and [current linker tunable documentation](https://sourceware.org/glibc/manual/latest/html_node/Dynamic-Linking-Tunables.html).

## Addons used by this fork

- **MultiAddonManager:** upstream builds distinct SteamRT3 and SteamRT4 assets. Its [build workflow](https://github.com/Source2ZE/MultiAddonManager/blob/main/.github/workflows/build.yml) packages `-steamrt3.tar.gz` and `-steamrt4.tar.gz` separately. [Release v1.5.4](https://github.com/Source2ZE/MultiAddonManager/releases/tag/v1.5.4) introduced RT4 builds for newer Linux environments; [v1.6](https://github.com/Source2ZE/MultiAddonManager/releases/tag/v1.6) migrated to KHook for Metamod past 1459 and warns against older Metamod versions. Runtime selection and Metamod/plugin version compatibility are separate requirements. Use a matching current asset/version pair and test workshop downloads, mounting, reconnects, and map changes.
- **S2Script:** its [release workflow](https://github.com/s2script/s2script/blob/main/.github/workflows/release.yml) builds in `rust:bullseye`, invokes `build-sniper.sh`, and rejects `s2script.so` or `libs2script_core.so` requiring glibc newer than 2.31. It publishes a single Linux archive. That provides a documented RT3 baseline; it does not certify RT4. Reuse may be possible, subject to dependency, load, FFI/hook, and gameplay tests.
- **GameFixes:** the [upstream Dockerfile](https://github.com/SlynxCZ/GameFixes_mm/blob/main/docker/Dockerfile) builds on the sniper SDK, and its [release workflow](https://github.com/SlynxCZ/GameFixes_mm/blob/main/.github/workflows/main.yml) packages one Linux build. No explicit RT4 certification or separate RT4 artifact was verified. Check its dependencies/stack flags and exercise enabled fixes on the target CS2 build.
- **Metamod:** test the exact build together with these addons. A successful loader start alone does not verify all hooks, signatures, or interfaces. No blanket AlliedModders RT4 certification was verified here.

CounterStrikeSharp, ModSharp, and Swiftly are outside the current fork's installed-addon scope; no migration conclusion for them is implied.

## Changes identified in the pre-migration repository

The pre-migration image used RT3 explicitly: [Dockerfile](https://github.com/s2script/s2script-cs2-egg/blob/9517796/docker/KitsuneLab-Dockerfile#L26). Both panel exports select this repository's `:stable` or `:beta` image; the separate Debian installation container only runs a dummy installation script. The Dockerfile builds `cs2egg` with `CGO_ENABLED=0`, so the Go entrypoint itself has no glibc dependency. The migration work is concentrated in the runtime image and native addon handling.

1. Replace the sniper platform base with a verified RT4 platform image, retain the rootfs-flattening workaround, and update labels, workflow wording, and runtime documentation. Confirm required existing tools (`sh`, `bash`, `useradd`, and SteamCMD prerequisites) in the resulting image. Publish the trial under an explicit experimental tag rather than advancing the fleet's `:stable` image immediately. See [Dockerfile](https://github.com/s2script/s2script-cs2-egg/blob/9517796/docker/KitsuneLab-Dockerfile) and [release workflow](https://github.com/s2script/s2script-cs2-egg/blob/9517796/.github/workflows/release.yml).
2. Change MultiAddonManager's runtime asset selection. [native.go](https://github.com/s2script/s2script-cs2-egg/blob/9517796/internal/egg/addons/native.go#L51) deliberately excludes RT4 and prefers RT3. The [existing addon test](https://github.com/s2script/s2script-cs2-egg/blob/9517796/tests/unit/egg/addons/native_test.go) puts an RT4 asset first to verify that it is rejected; this needs corresponding migration coverage.
3. Make runtime/asset identity part of native installation evidence, or provide an equivalent explicit migration. The current [receipt](https://github.com/s2script/s2script-cs2-egg/blob/9517796/internal/egg/addons/native.go#L387) records repository, release version, and file hashes, but no runtime/asset identity. The [up-to-date check](https://github.com/s2script/s2script-cs2-egg/blob/9517796/internal/egg/addons/native.go#L95) can retain a verified RT3 install at the same release tag after switching image/selector. Ensure the matching RT4 artifact is installed, and restore RT3 artifacts on rollback. Preserve operator configuration during replacement.
4. Validate both standalone and node-managed startup. [VPK sync](../modules/vpk-sync.md) runs SteamCMD on the host; changing the server container does not migrate that host process. The [node file cache](https://github.com/s2script/s2script-cs2-egg/blob/9517796/internal/node/addoncache/cache.go#L149) already keys files by download URL, allowing distinct RT3/RT4 asset URLs to coexist. Inspect pins and installed receipts rather than assuming the cache needs a new architecture.

Required acceptance evidence remains: clean image build and initial setup; standalone SteamCMD update; node-managed shared-file boot; vanilla CS2 boot and client connection; all plugins loaded and exercised; workshop content download and map transition; restart/update persistence; representative sustained load; and a tested RT3 rollback with the correct plugin binaries. The pre-migration release workflow only smoke-tested `cs2egg version`; that does not establish CS2 or addon compatibility.

Initial assessment: code changes are limited in scope, while binary compatibility testing and a reversible rollout are the main work. The user subsequently chose a complete RT4 migration for v2.0.0. That decision does not establish a performance improvement; any such claim still requires measurement.

## Follow-up: S2Script executable-stack compatibility

Inspection of the actual [S2Script v0.12.2](https://github.com/s2script/s2script/releases/tag/v0.12.2) archive installed into `dist/steamrt4-native-validation` found `s2script.so` marked `PT_GNU_STACK RWE`; `libs2script_core.so` was `RW`. The tested MAM v1.7.3 RT4 and GameFixes v1.0.18 libraries were also `RW`. An isolated `dlopen` probe in the built RT4 filesystem rejected the unmodified S2Script shim with `cannot enable executable stack as shared object requires: Invalid argument`. Starting the same probe with `GLIBC_TUNABLES=glibc.rtld.execstack=2` passed that barrier and reached the expected missing game symbol `g_pMemAlloc`. This establishes the stack-loading blocker and the tunable's effect, **not successful in-game plugin initialization or gameplay compatibility**.

The mechanism and tradeoff are documented upstream: glibc 2.41 stopped changing stack permissions when loading such a module dynamically. The [glibc 2.41 branch change adding tunable value 2](https://sourceware.org/pipermail/glibc-cvs/2025q2/087912.html) and [current manual](https://sourceware.org/glibc/manual/latest/html_node/Dynamic-Linking-Tunables.html) describe forcing an executable stack at process startup for this compatibility case. It weakens stack-execution protection for that process; it does not just grant an exception to one shared library. Values 0 and 1 do not provide the same compatibility behavior. A targeted setting for the CS2 launch preserves publisher binary bytes and avoids applying this policy to unrelated container processes. Explicit operator settings should remain authoritative, with an actionable error when they conflict with an installed shim that requests an executable stack.

Source investigation at the exact tag found a plausible metadata cause, but did **not prove complete object-level attribution or that clearing the final binary's flag is safe**:

- [The shim CMake configuration](https://github.com/s2script/s2script/blob/v0.12.2/shim/CMakeLists.txt) builds Breakpad's `breakpad_getcontext.S` into its static client library and links that library into the shim. The pinned [Breakpad assembly](https://github.com/google/breakpad/blob/9aebd3d8ef5a246deb2c929b5666aaba160ebce6/src/common/linux/breakpad_getcontext.S) lacks a `.note.GNU-stack` annotation. Its x86-64 implementation saves registers, calls `sigprocmask`, and returns; it does not visibly execute generated instructions on the stack. However, the final inspected shim has no retained `breakpad_getcontext` symbol. Archive extraction followed by section garbage collection may explain this, but no reproduced link map established it.
- [Private libffi configuration](https://github.com/s2script/s2script/blob/v0.12.2/shim/cmake/Libffi.cmake) pins libffi v3.7.1. Its [Unix x86-64 assembly](https://github.com/libffi/libffi/blob/5c1c43091ed611fdea774374355eb938c73a9157/src/x86/unix64.S) and [Win64 assembly](https://github.com/libffi/libffi/blob/5c1c43091ed611fdea774374355eb938c73a9157/src/x86/win64.S) explicitly declare a non-executable GNU stack. [Closure allocation](https://github.com/libffi/libffi/blob/5c1c43091ed611fdea774374355eb938c73a9157/src/closures.c) obtains executable trampoline memory separately. Executable trampolines do not by themselves imply a requirement for an executable process stack.
- All 84 members of the pinned [SDK protobuf archive](https://github.com/s2script/s2sdk/blob/cecdd5967906e9a409ce255aa3f30cfe7dada322/lib/linux64/release/libprotobuf.a) inspected with `readelf -SW` had a non-executable `.note.GNU-stack`. This rules out missing/executable annotations in that inspected archive, but is not a complete shim link audit.

A publisher-built shim with corrected stack metadata and an upstream stack-policy check is the preferred long-term resolution. For the current unmodified archive, the documented, narrowly applied startup tunable is an explicit compatibility compromise. Automatic flag clearing remains unjustified without a complete build/object audit and relevant hook, libffi, and crash-handler tests; a successful `dlopen` alone would not provide that evidence.
